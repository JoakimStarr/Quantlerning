> **前置知识：** p7-l1/l3 组合与风控；p5-l6 VaR；p3-l7 交易成本。
> **学完能做什么：** 说清一条信号从生成到对账要经过哪六步、每步的失效模式是什么；理解订单状态机与幂等性设计，能处理「超时未知单」；能按上线清单推进模拟盘 → 小资金试运行 → 逐级放大。

## 为什么回测跑通了还要模拟盘

回测（第三章）回答「过去表现如何」，模拟盘（Paper Trading）回答「现在能不能跑起来」。这两个问题听起来只差一个时间，实际上是两类完全不同的失败模式：回测的失败是**策略层面**的（赚不到钱），模拟盘暴露的是**工程层面**的（策略赚得到的钱，系统拿不到）。原因很简单：回测里你拥有上帝视角——数据永远准时、订单永远全额成交、进程永远活着；实盘里这三件事没有任何一件有保证。

下面把一条信号的一生拆成六步，逐步看哪几步回测覆盖了、哪几步只有模拟盘能暴露。

## 一条信号的生命周期

以「双均线金叉 → 买入茅台」为例，从信号到入账共六步：

**① 信号生成。** 行情数据到达 → 计算均线 → 判断金叉。**失效模式**：行情延迟或缺失——你以为在用 14:59 的价格，其实是 14:50 的；数据断流时信号引擎拿旧数据继续算，产生「幽灵信号」。回测里不存在这个问题（历史数据一次性给全），模拟盘里它是第一天就会撞上的墙。

**② 风控检查。** 信号要过风控层：单标的仓位上限、组合回撤熔断、当日最大下单次数。**失效模式**：信号被拒后怎么办？放弃、缩量还是排队？回测从来没有「拒单」这个概念，模拟盘必须把拒绝路径也写成代码（p7-l3 的「风控代码化」在这一步落地）。

**③ 订单构造与发出。** 把目标仓位换算成具体订单：买多少股（A 股整手约束）、用什么价格（市价还是限价，p7-l5）、发往哪个柜台。**失效模式**：资金计算与持仓对不上（昨日成交未清算）、API 超时后订单实际发出但本地以为失败——重复下单的来源。

**④ 撮合成交。** 订单进入交易所排队。**失效模式**：部分成交（只成交 40%，剩下的怎么办）、涨跌停无法成交（回测里「纸上成交」的现场版）、滑点超出假设（p7-l5 的订单簿现实）。回测假设「次日开盘价全额成交」，模拟盘会给这条假设开第一张罚单。

**⑤ 回报与对账。** 券商回报成交明细 → 与本地持仓核对。**失效模式**：理论仓位 vs 实际持仓不一致（重复下单、部分成交漏记）。对账不一致是实盘最危险的信号之一——连「我现在有多少仓位」都不确定，后面所有计算都是空中楼阁。

**⑥ 记录与复盘。** 全程留痕：信号快照、订单、回报、当时的持仓与净值。**失效模式**：没记当时的行情快照，事后想复盘「当时为什么下单」却无据可查——这违反 p3-l1「可归因」的要求，也违反 p7-l3「风控可审计」的要求。

看清了吗？**回测只覆盖了第①步和第④步的理想化版本**；②③⑤⑥四步，加上①④的现实版本，全部是模拟盘的管辖范围。这就是「回测漂亮 ≠ 实盘能跑」的精确含义。

## 订单状态机与幂等性：第③④⑤步的工程核心

六步里最容易出事的是「订单发出去之后」的这段时间。工程上的解法有两件套：

**第一件：唯一标识（幂等性）。** 每笔订单发出前先分配一个**本地唯一单号**（client order id），随订单发往柜台。之后无论重发多少次，柜台都按同一单号去重——这就是**幂等**：同一操作执行多次与执行一次效果相同。没有它，「API 超时后不确定订单是否已发出」就只能靠猜；有了它，重发是安全的，重复成交被柜台挡住。

**第二件：订单状态机。** 每笔订单在本地维护一个状态，只允许沿固定路径流转：

```
待发 → 已发 → 部分成交 → 全部成交
              ↘ 已撤/已拒
关键：还有第六个状态——「未知」（超时且未收到回报）
```

处理「未知」态的规则只有一条：**先查证，再行动**。超时后立刻用 client order id 向柜台查询订单状态，按查到的真实状态更新本地——查到「已成交」就补记回报，查到「不存在」才允许重发。**绝不允许在未知状态下直接补单**：那笔「失败」的订单可能正在排队，补单就是双倍仓位。这一条规则是所有实盘事故里出现频率最高的教训。

本地状态永远以**券商回报为准**，本地推断只用于触发查询——这就是第⑤步对账能对上的前提。

## 监控与告警：沉默即异常

模拟盘与实盘运行中，系统大部分时间「没有消息」——而**没有消息本身就是需要监控的信号**。四类必须配告警的沉默：

- **行情心跳**：超过 $N$ 秒没收到行情推送（数据断流 → 幽灵信号的源头）；
- **回报延迟**：订单发出后 $N$ 秒未收到回报（进入「未知」态，触发查证流程）；
- **净值偏离**：实时净值与预期净值偏离超过阈值（可能有订单漏记或价格异常）；
- **对账差异**：理论持仓 vs 实际持仓不一致——**任何**非零差异都应立即告警并停止新开仓。

告警要送到「你一定会看到的地方」（短信/电话级别，而不是只在日志里），且熔断触发必须伴随告警（p7-l3 的三层熔断若静默触发，等于没有熔断）。

## 模拟盘 vs 回测 vs 实盘

| | 回测 | 模拟盘 | 实盘 |
|---|---|---|---|
| 数据 | 历史（已知结局） | 实时/滚动（未知结局） | 实时（真金白银） |
| 成交 | 假设（次日价/收盘价、全成） | 真实规则 + 滑点（虚拟资金） | 真实规则 + 真实冲击 |
| 风控 | 可以没有 | 必须代码化 | 必须代码化 + 熔断 |
| 失败代价 | 重跑 | 重启 | 亏损、不可逆 |
| 回答的问题 | 过去表现如何 | 现在能不能跑起来 | 现在正在赚钱还是亏钱 |

注意「失败代价」这一行：回测错了可以重跑，模拟盘错了可以重启，实盘错了就是亏损离场。**系统工程的投入应该与失败代价成正比**——这正是模拟盘存在的意义：用最低的成本把⑥步链路走扎实。

## 从模拟盘到券商 API：接口怎么接

- **账户与权限**：券商 API 需单独申请，权限分级（只读查询 → 模拟交易 → 实盘）——每一级都用够时间再申请下一级；
- **接口形态**：多数 A 股券商提供 Python SDK（QMT、miniQMT、掘金）或 REST/WebSocket 接口；
- **最小原则**：先用「只读 + 手动下单」跑通，再逐步自动化——第一次接 API 就全自动下单，等于把上面六步的所有失效模式一次性引爆破仓；
- **测试环境**：券商通常提供模拟环境，先在模拟环境验证接口与撮合规则，再接自己的模拟盘。

## 风控必须代码化：熔断的三个层级

实盘风控不能依赖人工纪律——亏损发生时人工恰恰最不可靠。按响应速度分三层写进代码（p7-l3 的工具在这一步变成守门员）：

1. **单笔层（毫秒级）**：单笔订单量上限、价格偏离保护（限价单价格带）、当日最大下单次数——挡住「信号抖动导致的高频乱单」；
2. **组合层（日内）**：组合日内回撤熔断——跌破阈值程序化减仓/清仓（p7-l3 的止损在此执行）；
3. **账户层（持续）**：总回撤熔断、最大持仓集中度、异常自动停止交易并告警——最后一道保险丝。

每一层都要有**告警**跟随：熔断触发不是静默的，必须立刻通知到你。

## 逐级放大：小资金试运行后的闸门

上线清单的最后一步是小资金试运行——但试运行之后怎么放大，也需要规则而不是胆量。**逐级放大闸门**的思路：每次放大（如仓位翻倍）前，必须同时满足一组量化条件，任何一条失守就停止放大甚至回退：

- **连续 $N$ 周（如 8 周）实盘 Sharpe $>0$**，且未触发任何熔断；
- **实际成本率与模拟盘假设的偏差 < 50%**（如假设 5bp、实测不超过 7.5bp，p7-l5 会解释为什么冲击成本随规模非线性上升）；
- **对账零差错**，订单「未知」态每次都被查证解决；
- **无未处理的告警**。

闸门的意义与 p6-l5 的验收清单同源：**放大决策也要有规则，否则「试运行通过」会退化成「自我感觉良好」**。同时记住冲击成本的非线性——仓位翻倍后，同样的信号对订单簿的冲击远大于翻倍（p7-l5），所以每放大一级都要重新校准成本假设。

## 上线清单

- [ ] 模拟盘稳定运行 ≥ 1 个月，覆盖涨跌停、停牌、长假前后的成交窗口
- [ ] 六步链路各步的失效模式都有代码化处理（拒单、超时、部分成交、对账不一致）
- [ ] 订单状态机含「未知」态，查证流程与 client order id 幂等重发验证通过
- [ ] 券商 API 只读权限验证通过
- [ ] 三层风控全部代码化并通过压测（故意制造异常订单验证熔断会触发）
- [ ] 四类监控告警通道（行情心跳/回报延迟/净值偏离/对账差异）验证
- [ ] 小资金实盘试运行（如 1% 仓位），用真实滑点校准回测假设（p7-l5）
- [ ] 逐级放大闸门条件已定义，且当前状态满足或明确不满足

**练习 2（选择题）：** 六步链路的归属。

:::quiz
Q: 「订单发出后 API 超时，本地以为失败但订单实际已成交」这类问题，属于信号生命周期六步中的哪一步、哪类环境才能暴露？
- 第①步信号生成，回测就能暴露
- 第③④步订单构造与撮合，只有模拟盘/实盘能暴露
- 第⑥步记录复盘，与成交无关
- 任何回测都能暴露
A: 2
E: API 超时与「订单状态不确定」是工程层失效：回测没有 API、没有超时，只有模拟盘/实盘才存在——这正是「回测覆盖不到后三步」的具体例子。
:::

**练习 3（选择题）：** 订单状态机的「未知」态。

:::quiz
Q: 订单发出后 API 超时、本地进入「未知」态，正确的处理是？
- 立即按原价补单，保证仓位到位
- 先用 client order id 向柜台查证订单状态，按真实状态更新本地，再决定是否重发

- 撤销所有未完成订单并重启系统
A: 2
E: 那笔「失败」的订单可能正在排队——未知态直接补单就是双倍仓位；幂等单号 + 先查证再行动是唯一安全路径。
:::

**练习 4（选择题）：** 幂等性的作用。

:::quiz
Q: 给每笔订单分配唯一 client order id（幂等重发），解决的核心问题是?
- 加快下单速度
- 同一订单重发多次也只成交一次，使「超时重试」变得安全
- 降低佣金
- 提高成交概率
A: 2
E: 幂等 = 同一操作执行多次与一次效果相同；柜台按单号去重后，超时重试不再有重复成交风险——这是第③步失效模式的工程解。
:::

**练习 5（选择题）：** 「沉默即异常」。

:::quiz

- 行情推送已 60 秒未到达
- 订单发出 10 秒未收到回报
- 实时净值与对账后的理论净值出现 0.5% 偏差

**练习 6（应用题）：** 核算模拟盘滑点成本。

:::exercise
T: 模拟盘假设单边滑点 5bp（0.05%）。某策略每月调仓 2 次，每次调仓含 1 买 1 卖，组合规模 100 万元。请计算每月滑点成本占组合的比例与金额；若实盘实际单边滑点为 15bp，成本如何变化？这提示模拟盘应如何设置滑点假设。

追问：若该策略年化收益目标为 $8\%$，按每月 $0.2\%$ 的滑点成本折算，年化滑点成本占收益目标的比例是多少？再把调仓频率提高到每月 4 次，比例又变为多少？请用这两个数字说明调仓频率与交易成本的权衡，以及为何高频策略对滑点极其敏感。

:::answer
- **主答**：每月成交 $=2$ 次 $\times2$ 笔 $\times100$ 万 $=400$ 万；滑点 $=400$ 万 $\times5\text{bp}=2000$ 元、占 $0.2\%$。实盘 15bp：6000 元、$0.6\%$——**3 倍**。
- **追问**：年化滑点 $2.4\%$，占 8% 目标的 30%；4 次/月：$4.8\%$、占 60%——频率翻倍成本翻倍。启示：滑点假设按实盘可验证的保守值设定（试运行实测回填），策略先过「目标收益 vs 换手成本」的算术关——这正是模拟盘要暴露的第一类问题。
:::
:::

- 由券商柜台人工把关

**练习 8（应用题）：** 小资金试运行成本核算。

:::exercise
T: 上线清单要求小资金试运行（如 1% 仓位）。总资金 50 万元，试运行 1% 即 5,000 元；1 个月累计成交额 20 万元，实际滑点与冲击成本合计 400 元。

① 请计算实际成本率，与模拟盘假设的单边 5bp 对比，并说明小资金试运行的意义；
② 若试运行后把仓位放大到 100%，为什么「把实测成本率直接乘以资金」会低估真实冲击成本？
③ 按「逐级放大闸门」的思路，给出至少三条放大前必须满足的条件，以及任一条件失守时的动作。

:::answer
- **①** 实际成本率 $=400/200000=20\text{bp}$，是假设 5bp 的 **4 倍**。意义：小资金试运行用最小代价实测真实摩擦（滑点、冲击、部分成交、API 异常）。
- **②** 成本率不能线性放大：订单规模增大后占订单簿深度的比例上升，冲击按超线性增长（p7-l5 的 $\sqrt{Q/ADV}$ 量级），且需要拆单——100% 仓位的单笔冲击远高于 1% 仓位实测值，应按「分档规模 × 冲击函数」重估。
- **③** 闸门示例：连续 8 周实盘 Sharpe>0 且未触熔断；实测成本率与假设偏差 <50%；对账零差错、「未知」订单全部查证解决；无未处理告警。任一失守：停止放大；若成本率或对账失守，回退到上一级仓位并排查原因，而不是「再观察一周」。
:::
:::

Q: 模拟盘稳定运行 1 个月、信号与风控都正常，此时最合理的判断是？
- 已充分验证，可直接上实盘
- 只证明了全链路「跑得通」，滑点/流动性/情绪等实盘差距仍需小资金试运行检验
- 回测结论自动成立
- 模拟盘收益可直接当作实盘预期
A: 2
E: 模拟盘回答「现在能不能跑起来」，不回答「实盘能不能赚」；模拟盘假设的滑点常被实盘超越（练习 8 实测约 20bp），情绪与部分成交也无法模拟——上线清单把小资金试运行放在最后一步，正是为暴露这些差距。
:::

**练习 10（应用题）：** 为一个策略设计完整的上线时间表。

:::exercise
T: 你有一套双均线策略，回测已通过（时间切分、对照组齐全）。请设计从模拟盘到目标仓位的完整时间表：

① 模拟盘阶段要覆盖哪些市况与验证项？时长建议多少？
② 小资金试运行（1% 仓位）要实测哪些数字？用它们回填什么假设？
③ 逐级放大（1%→5%→20%→100%）的闸门条件与回退规则；
④ 每一级放大后，必须重估的是哪一类成本？为什么它随规模非线性变化？

:::answer
- **①** ≥1 个月（建议 2~3 个月），覆盖涨跌停、停牌、长假前后、开盘集合竞价等成交窗口；验证项：六步链路失效模式处理、订单状态机与未知态查证、三层熔断压测、四类告警、只读权限。
- **②** 实测：单边滑点与冲击成本、部分成交比例、信号到成交的延迟、拒单率、对账差错次数；用它们回填回测的成本假设与成交假设（回测按新假设重跑，确认策略仍成立）。
- **③** 每级闸门：连续 8 周 Sharpe>0、未触熔断、成本率偏差 <50%、对账零差错、无未处理告警；全部满足才放大（1%→5%→20%→100% 逐级），任一失守停止放大，成本或对账失守则回退上一级并排查。
- **④** 冲击成本：订单规模占订单簿深度的比例随仓位上升，冲击超线性增长且需拆单（p7-l5）——每放大一级都要用新规模的实测/估算重新校准成本假设，而不是沿用上一级的实测值。
:::

## 本章生态：实盘工程生态

- **平台与接口**：VeighNa（vn.py，开源交易框架：网关/风控/事件引擎齐全）、QMT/miniQMT 与掘金量化（券商侧 Python 接口）、PTrade（恒生）——接口能力差异大，选型先看「回报推送是否实时、是否支持模拟环境」；
- **监控与运维栈**：行情/回报心跳检测、对账脚本（日终 vs 券商交割单）、告警通道（短信/电话级）；开源可用 Prometheus + Grafana 搭监控面板——量化系统的运维与互联网服务同类，「服务不可观测 = 不可运行」；
- **工程纪律**：所有实盘代码走版本管理与灰度发布（先模拟盘跑新版本再切实盘）；回测引擎与实盘执行引擎**共用同一套信号代码**，避免「回测一套逻辑、实盘另一套逻辑」的口径漂移。
